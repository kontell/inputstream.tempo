v21.4.2
- Playback-speed keys (PgUp/PgDn) and the speed dialog work again for add-ons
  that keep their rate in a file of their own. speed.py read the shared
  special://temp/inputstream_tempo regardless of what the sentinel named, so a
  key press wrote a new rate into a file nothing was polling: the script ran,
  Kodi logged it as successful, and the stream carried on at the old speed. It
  now takes tempo_file and config_file from the sentinel, falling back to the
  shared paths when the sentinel does not name them.
- A sentinel left behind by a previous run is cleared at startup, so the keys
  are not live for playback that has nothing to do with tempo.

v21.4.1
- Seeks no longer lose the first packets of the new position. SeekTime's
  probe for where the seek landed read them and freed them, so every decoder
  started mid-GOP after a seek: "[hevc] Could not find ref with POC" bursts on
  software decode, concealed on most hardware decoders, and a wedged AV1
  decoder on a Pixel 7 (inherited from upstream ffmpegdirect; Kodi's own
  demuxer keeps its probe packet). They are now queued and delivered first.

v21.4.0
- Tempo now covers video. Video and subtitle packets are projected through the
  same content↔output time map (src/stream/TempoMap.h) that the stretched
  audio walks, so a video item stays in A/V sync at any rate. The data is
  untouched; only timestamps move.
- The map's offset (content − output) is continuous across seeks and flushes,
  so Kodi's own accurate-seek arithmetic (startpts = target − time_offset)
  and the OSD stay right; SeekTime returns startpts in the packets' domain.
- INPUTSTREAM_SUPPORTS_IPOSTIME is advertised for video items, so VideoPlayer
  hands seek targets over in content time instead of shifting them by
  time_offset. PosTime seeks backward to the keyframe (Kodi drops its
  backward flag on that path) and now passes milliseconds, not seconds.
- Time is reported at the playing point: GetTimes() reads the map
  queue_secs behind the demux head (new property inputstream.tempo.queue_secs;
  8 on Omega, pass Kodi 22's videoplayer.queuetimesize on Piers), so a
  running tempo change no longer biases the reported position by
  (rate − 1) × queue depth. Audio-only items keep the old head reading.
- The audio pipeline follows Kodi's audio-track selection: every audio
  stream is advertised as PCM f32 and OpenStream re-targets the decoder and
  atempo graph to the track Kodi opens; the other tracks are discarded at the
  demuxer.
- The audio counters anchor on the first decoded frame's own timestamp
  rather than the packet dts, so codec priming (AAC, MP3) no longer makes the
  PCM lead the picture by ~40 ms.
- The tempo file is polled by wall clock (250 ms) instead of every 50 reads,
  and each applied change, anchor and re-target is written back atomically to
  <tempo_file>.state as a one-line JSON record.
- The wall-clock throttle no longer sleeps inside DemuxRead for video items
  (that is VideoPlayer's own loop); Kodi's queues pace video. The optional
  inputstream.tempo.lead_secs property re-enables a lead bound for video,
  implemented as empty packets with a 10 ms nap.
- The initial seek hold (start_time) is not armed for video items —
  VideoPlayer seeks before output starts, so it would only delay the picture.
- Video stream info now carries colour space, range, primaries and transfer
  characteristics (HDR10 signalling); upstream reports them unspecified.
- Service window properties now also update while video is playing.
- New: tests/tempomap_test.cpp, a dependency-free check of the map.
- Fix a crash on the first tempo-file poll inside the flatpak Kodi (and any
  Kodi whose libstdc++ differs from the build host's): the Linux build links
  libstdc++ statically but exported its symbols, so std::ifstream bound across
  two libstdc++ copies and jumped into typeinfo. The tempo and state files now
  go through C stdio, and the Linux link hides the static runtime
  (-Wl,--exclude-libs,ALL). Present since the first Linux release.
- New: tests/live/tempo_checklist.py, the JSON-RPC driver for the video
  checklist (rate slope, dead time, readout step, seeks, audio-track switch,
  renderer rebuilds), local or over adb.

v0.3.5
- Revert v0.3.4 dynamic ptsStart. That approach read state from internal
  m_tempoOutputPts/m_tempoContentPts counters that advance on packet
  EMISSION. When demux runs ahead of audio consumption (e.g. ActiveAE
  stalls), those counters overstate elapsed content, so ptsStart drifts
  beyond any sensible value and state.time = clock − ptsStart explodes
  past tempo rate (observed OSD racing far beyond 2× at 2× tempo).
- Return to v0.3.3 approach: GetTimes returns false when tempo is active,
  VideoPlayer falls through to its IDisplayTime branch. That branch uses
  state.dts and m_CurrentAudio.dispTime, which VideoPlayer populates
  AFTER consuming packets — so the derived offset tracks actual playback
  position rather than emission.

v0.3.4
- VideoPlayer: OSD progress now reports content position at non-1x tempo.
  v0.3.3 tried routing via the IDisplayTime branch (returning false from
  GetTimes so VideoPlayer would use dispTime - dts) but state.time still
  advanced at wall-clock rate. Switched to the ITimes branch with a
  dynamic ptsStart = (m_tempoOutputPts - m_tempoContentPts), so
    state.time = (clock - ptsStart) / 1000
               = output - (output - content) = content
  directly, without relying on dispTime propagation. ptsStart refreshes
  on every emitted packet, so it tracks live tempo changes. Non-tempo
  playback is unaffected.

v0.3.3
- VideoPlayer: make progress display follow tempo changes. GetTimes()
  now returns false when tempo is active, so VideoPlayer routes through
  its IDisplayTime branch (state.time += dispTime - dts) instead of
  the ITimes branch (state.time = wall-clock). The ITimes path ignores
  dispTime entirely and progress would advance at wall-clock rate
  regardless of tempo. Non-tempo playback is unaffected.

v0.3.2
- Fix audio glitching under VideoPlayer at non-1× tempo. v0.3.1 made
  packet pts/dts/duration advance by content time, which broke ActiveAE's
  wall-clock sync (packet PTS grew faster than samples drained, triggering
  hard resyncs every ~1-2s at 2× tempo). Now two separate PTS streams:
    - packet.pts/dts/duration → output (wall-clock) time, for ActiveAE
    - packet.dispTime (ms) + m_currentPts → content time, for OSD and
      GetTime() / PAPlayer resume.
  VideoPlayer reads dispTime for its progress display; PAPlayer reads
  GetTime() via ICodec — both now get content time, audio stays in sync.

v0.3.1
- Tempo PTS tracking: advance m_tempoOutputPts by content duration
  (output duration × m_currentTempo) instead of output duration.

  (with the ICodec::GetTime() addition in Kodi master) and VideoPlayer

v0.2.21

  x86_64 host. --host tells autoconf to skip AC_TRY_RUN. Triplet exported
  from build.sh as AUTOCONF_HOST per target.

v0.2.20
- Fix cross-compile for autoconf-based deps (gnutls, nettle, gmp, iconv,
  libzvbi, bz2, xz-utils). Their CMakeLists.txt invokes configure without
  passing CC=, so autoconf was detecting the host gcc and building
  x86_64 archives that the cross linker rejected ("libgnutls.a is
  incompatible with armelf_linux_eabi"). Export CC/CXX/AR/STRIP/RANLIB
  pointing at the cross toolchain in build.sh before invoking make;
  configure inherits these and builds for the target arch. CMake-based
  deps already use the toolchain file and are unaffected.

v0.2.18
- ffmpeg configure is now launched via a generated wrapper script that
  explicitly exports PKG_CONFIG_PATH / PKG_CONFIG_LIBDIR and prints a
  diagnostic dump first. Previous cmake-level attempts (bash-style VAR=val

v0.2.17
- Also set PKG_CONFIG_LIBDIR for ffmpeg configure, not just PKG_CONFIG_PATH.
  On Ubuntu CI runners the host system has gnutls.pc at the default pkg-
  config path, so PKG_CONFIG_PATH alone let pkg-config fall back to host
  libs which the Android/ARM cross-linker can't resolve. LIBDIR replaces
  the default search path so pkg-config pins to the cross-built libs only.

v0.2.16
- Fix cross-compile pkg-config discovery in ffmpeg configure: wrap the
  configure command with `cmake -E env PKG_CONFIG_PATH=...` instead of the
  bash-style env-var prefix, which doesn't survive CMake's execute_process
  in cross-compile contexts. Was masked on native x86_64 because system
  pkg-config paths already contained gnutls.pc.

v0.2.15
- Fix Android ffmpeg configure: override CMAKE_C_COMPILER to the NDK's
  per-target wrapper (e.g. armv7a-linux-androideabi21-clang) which bakes
  the target triple in. Upstream NDK sets CMAKE_C_COMPILER to plain clang
  and puts the target in CMAKE_C_COMPILER_TARGET; ffmpeg's configure only
  consumes --cc=${CMAKE_C_COMPILER} so the target was lost and clang
  couldn't create executables during the configure-time test.

v0.2.14
- Fix Android cross-compile: set CPU as a CACHE var in the toolchain file so
  it survives into dep external_projects. Kodi's HandleDepends.cmake doesn't
  forward -DCPU through BUILD_ARGS, so ffmpeg's CMakeLists previously saw
  CPU as empty and fell through to --cpu=i686 --disable-mmx, breaking the
  ARM clang.
- Revert the libzvbi LIBS=-liconv change for non-Android hosts (it broke
  fresh Linux runners — Ubuntu's glibc supplies iconv via libc, so adding
  -liconv made the configure-time compiler test fail).
